# AGENTS.md

This file provides guidance to coding agents when working with code in this repository.

## What this repo is

Personal dotfiles: Homebrew packages, zsh, [starship](https://starship.rs/) (shell prompt), [yazi](https://yazi-rs.github.io/) (terminal file manager), Neovim, [lazygit](https://github.com/jesseduffield/lazygit) config, IdeaVim config for JetBrains IDEs, and Claude Code settings. Files under `zsh/`, `starship/`, `nvim/`, `yazi/`, `lazygit/`, `ideavimrc/`, and `claude/` are symlinked into `$HOME` (or, for lazygit, `~/Library/Application Support`; for `claude/`, `~/.claude`) — they are not copied — so an edit here takes effect on next shell/app restart, no install step required for iterating.

## Commands

```sh
./install.sh                                          # (re)create all symlinks + `brew bundle` + `ya pkg install`
brew bundle dump --force --describe --file=Brewfile    # regenerate Brewfile from currently installed packages
cd yazi && ya pkg add <owner>/<repo>[:<pkg>]            # add a yazi flavor/plugin (writes package.toml)
cd yazi && ya pkg upgrade                               # upgrade all yazi flavors/plugins in package.toml
```

There is no build, lint, or test step — this is plain config, not a program.

To check a change without touching the real system, symlink into a scratch `$HOME` instead of running `install.sh` directly:

```sh
HOME=/tmp/dotfiles-test ./install.sh
```

## Restoring this environment on a new Mac

The intended entry point is a single prompt to Claude Code on a fresh machine (see README), so an agent may be reading this right after cloning. Do it in this order and report what happened at each step:

1. **Homebrew.** If `command -v brew` fails, install it with the official one-liner from https://brew.sh. The installer asks for the user's macOS password: hand that prompt to the user (they can run the command themselves with Claude Code's `!` prefix) — never try to supply or pipe a password. Afterwards load it into the current shell with `eval "$(/opt/homebrew/bin/brew shellenv)"`; `zsh/.zprofile` takes over from the next login shell.
2. **Clone.** `git clone https://github.com/SJ-Wu/dotfiles.git ~/Github/dotfiles`, or `git -C ~/Github/dotfiles pull` if it already exists.
3. **Install.** Run `./install.sh` from the repo root. It is idempotent, so re-running after a failure is safe.
4. **Verify.** `brew bundle check --file=Brewfile`, then `ls -la` the link targets listed in `install.sh` and confirm each points back into the repo. Report anything missing instead of patching around it.
5. **Hand back.** An agent's shell cannot replace the user's, so tell the user to run `exec zsh` (or open a new Ghostty window). Also tell them about the steps that need a human: granting Karabiner-Elements its macOS permissions in System Settings, and logging in to `gh` (`gh auth login`).

## Architecture

- **`install.sh`** is the only thing that ties the repo to the live system. It's a single idempotent symlink step (`link()`  function) mapping repo path -> `$HOME` path, followed by `brew bundle`. Any new dotfile must be added there explicitly — nothing is auto-discovered. It backs up a pre-existing real file/dir once as `<name>.bak-<timestamp>` before linking; an already-correct symlink is left alone.
- **`Brewfile`** is the single source of truth for installed CLI tools/casks. Keep it in sync with the real system via `brew bundle dump`, don't hand-edit it out of sync with what's actually installed.
- **`nvim/`** follows the standard lazy.nvim layout: `init.lua` only requires three modules in order — `config.options`, `config.keymaps`, then `config.lazy` (which bootstraps lazy.nvim itself and calls `require("lazy").setup("plugins")`). Every file under `nvim/lua/plugins/` is auto-loaded as a lazy.nvim plugin spec — add a plugin by dropping a new file there, nothing to register elsewhere. Keep `init.lua` thin; real settings belong in `lua/config/*` or a plugin spec.
- **`yazi/`** config files (`yazi.toml`, `keymap.toml`, `theme.toml`, `init.lua`) are merged on top of yazi's built-in defaults, not a full replacement — only put overrides here, not the complete default set. Flavors/plugins are managed by yazi's own package manager (`ya pkg`): `yazi/package.toml` is the lockfile (committed), but `yazi/flavors/` and `yazi/plugins/` themselves are fetched by `ya pkg install`/`install.sh` and gitignored — never hand-edit or commit into those two directories, and don't forget a plugin usually needs wiring in *two* places: `init.lua` (`require("<plugin>"):setup{...}`) and/or `keymap.toml` (bind a key to `plugin <name>`).
- **`zsh/.zprofile`** vs **`zsh/.zshrc`**: `.zprofile` runs once per login shell (PATH/env setup only, e.g. Homebrew shellenv); `.zshrc` runs for every interactive shell (tool init like `fzf`/`zoxide`, functions, aliases). The SDKMAN block at the end of `.zshrc` must stay the last thing in the file — SDKMAN's own installer enforces this. `.zshrc` also carries `_auto_venv`, a `chpwd` hook that walks up from `$PWD` to find the nearest `.venv` and activates/switches/deactivates it; it is deliberately on `chpwd` rather than `precmd` (once per directory change, not once per prompt), and it must keep returning 0 on every path — it runs once at the end of `.zshrc`, and a non-zero status there would make starship paint the first prompt's `❯` red. Its `_deactivate_venv` helper handles `VIRTUAL_ENV` inherited from a parent process, where the venv's own `deactivate` function does not exist. The prompt side is `[python]` in `starship/starship.toml`, which reads `$VIRTUAL_ENV`.
- **`starship/`** holds `starship.toml`, the prompt config, symlinked to `~/.config/starship.toml` (starship's default location) and initialised by the `eval "$(starship init zsh)"` line in `.zshrc`. Two things about this file bite when editing it: (1) once `format` is customised, *only* the modules named in it render — a module with a config block but no `$module` in `format` is silently dead (and, usefully, not even computed); (2) module variables are lazily evaluated, so a `format` that omits `$version` never runs the version-detection command at all. That's why `[java]` deliberately prints only its symbol — resolving the version means actually running `java -Xinternalversion`, a 200-400ms JVM cold start on every prompt in a Java repo. Measure with `starship timings` before adding anything that shells out. Nerd Font glyphs are written as `\uXXXX`/`\UXXXXXXXX` escapes to keep the file pure ASCII; those only unescape inside TOML *basic* strings (double-quoted), never inside single-quoted literal strings.
- **`tmux/`** holds `tmux.conf`, symlinked to `~/.config/tmux/tmux.conf` (tmux 3.1+ reads that XDG path, so there is no `~/.tmux.conf`). The Ghostty block (`allow-passthrough`, `default-terminal "tmux-256color"`, `terminal-features`) is load-bearing: without it, yazi's terminal-capability probes leak into the pane as junk keystrokes. `escape-time` and `focus-events` are there for Neovim (`:checkhealth` flags both). Pane movement is `prefix + h/j/k/l` to match the Vim bindings elsewhere in this repo; status-line colors are the same Tokyo Night palette as `nvim/`, `yazi/` and `lazygit/`. Validate edits without touching a running server: `tmux -L cfgtest -f tmux/tmux.conf new-session -d && tmux -L cfgtest kill-server`.
- **`vimrc/`** is the config for the *system* vim (`/usr/bin/vim`), not Neovim — it is for `sudo vim`, ssh'ing to another box, and quick edits, while `nvim/` stays the main editor. Deliberately **zero-dependency**: no plugin manager, no bootstrap, nothing outside a single `~/.vimrc`, so the file can be scp'd anywhere and still work. Keep it that way — reach for a vim 9 built-in (`packadd! matchit`) or a hand-rolled function before adding a plugin. Key bindings mirror `ideavimrc/` for muscle memory; where a vim built-in had to be sacrificed or an IdeaVim action has no vim equivalent, it is listed in the two comment blocks at the end of the file — update those when changing bindings.
- **`ideavimrc/`** is the IdeaVim config for JetBrains IDEs. Two symlinks: `ideavimrc/.ideavimrc` -> `~/.ideavimrc` (the entry point IdeaVim reads) and the whole directory -> `~/.config/ideavim` (so the entry file can `source` its siblings by a stable path). `.ideavimrc` holds everything shared and ends with an `if &ide =~? ...` block that auto-sources `py_ideavimrc` under PyCharm, `java_ideavimrc` under IntelliJ IDEA, or `js_ideavimrc` under WebStorm; `zij`/`zpc`/`zws` source them manually. Language-specific files must stay free of duplicated common mappings. Verify action names with `:actionlist <keyword>` inside the IDE before adding an `:action` mapping - a wrong name fails silently.
- **`karabiner/`** is the [Karabiner-Elements](https://karabiner-elements.pqrs.org/) config. The **whole directory** is symlinked to `~/.config/karabiner`, never the single `karabiner.json` — `Karabiner-Console-User-Server` rewrites that file by writing a temp file and renaming it over the top, which replaces a file symlink with a real file and silently detaches the repo. A directory symlink survives that. Consequence: any change made in the Karabiner GUI shows up directly as a diff here, so commit it rather than hand-editing the JSON to match. `karabiner/automatic_backups/` is Karabiner's own backup churn and is gitignored. Karabiner does **not** hot-reload edits made through the symlink — its file watcher never fires, so after editing `karabiner.json` here you must run `launchctl kickstart -k "gui/$(id -u)/org.pqrs.service.agent.Karabiner-Console-User-Server"` to make it re-read. Skipping that leaves a stale config in memory, and the next change made in the GUI serializes that stale copy back over your edit. Verify with `"/Library/Application Support/org.pqrs/Karabiner-Elements/bin/karabiner_cli" --show-current-profile-name` and by checking for a fresh `Load .../karabiner.json` line in `~/.local/share/karabiner/log/console_user_server.log`.
- **`claude/`** holds Claude Code's global config: `settings.json` (symlinked whole, so it's the single source of truth for `~/.claude/settings.json` — don't hand-edit the live file out of sync) and `statusline.sh`, the script `settings.json`'s `statusLine.command` points at. The script reads a JSON payload on stdin (see `code.claude.com/docs/en/statusline` for the schema) and prints three ANSI-colored lines to stdout: identity (folder, branch, model/effort, and the IDE name when a live `~/.claude/ide/*.lock` has this project open), then quotas (context, 5h, 7d — each colored green/yellow/red by how much is left), then dim session stats (cost, lines +/-, cache hit ratio, duration, session name). Two things to preserve when editing it: it runs under `set -euo pipefail`, so every command substitution that can legitimately fail needs an explicit `|| true` — otherwise one bad `git`/`jq`/`date` call aborts the script and the whole status line renders blank instead of just losing a field; and in jq, `startswith()`'s argument is evaluated against *its own* input, so matching a workspace folder against a project path must bind the folder to a variable (`. as $f`) first; it must stay executable (`chmod +x`) since `settings.json` invokes it by path, not via `bash`. The `hooks` block in `settings.json` is **not hand-written**: Orca (the `stablyai/orca` cask) writes its own 12 hooks there on install, straight through the symlink and therefore straight into this repo — the same hazard as `karabiner/` above, minus the GUI. Leave that block alone and let Orca own it; it re-emits it anyway, and each hook no-ops on a machine without `~/.orca/agent-hooks/`. Orca also drops a `claude/settings.json.bak` next to it, which `.gitignore` covers. `enabledPlugins` and `extraKnownMarketplaces` are the same story: Claude Code writes them itself when a plugin is installed from a marketplace, so a marketplace-installed skill is recorded here simply by installing it — commit the resulting diff rather than hand-writing the entry (Claude Code also reorders the top-level keys when it rewrites the file, which is why such a diff looks bigger than it is). A plugin from the built-in official marketplace needs only its `enabledPlugins` line; a third-party one needs the matching `extraKnownMarketplaces` source too, since that is all a fresh machine has to go on to find the repo. Nothing further is needed to bootstrap them: once `install.sh` has linked `settings.json`, Claude Code fetches the listed plugins into `~/.claude/plugins/` on next start, and it owns that cache — never vendor a marketplace skill into a repo of your own.
